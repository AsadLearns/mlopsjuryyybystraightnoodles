1. Executive Summary & Objective

In production machine learning systems, model training represents only 15–20% of the entire lifecycle. The remaining 80–85% is governed by Machine Learning Operations (MLOps):

  1. Model Serialization: Converting research models into secure, portable, runtime-optimized formats (.pkl, .pt, .onnx).
  2. Mathematical Parity: Proving zero accuracy degradation across runtimes (< 10-6 divergence).
  3. Dual Deployment Paradigms: Benchmarking ultra-low-latency Edge Inference (sub-millisecond ONNX Runtime) vs. scalable Cloud Microservices (FastAPI + Docker).
  4. CI/CD Automation (GitHub Actions): Automated linting + unit tests on PRs, automated model training on push to main, and automated container build & staging deployment on release tags (v*.*.*).
  5. Workflow Orchestration (Apache Airflow): Automated DAG for Data Download → Preprocessing → Training → Evaluation → Conditional Accuracy Improvement Gating (BranchPythonOperator) → Deployment.

6. Problem-Based Learning (PBL): GitHub Actions CI/CD Pipeline

We built a multi-stage CI/CD pipeline in .github/workflows/mlops_ci_cd.yml meeting all enterprise criteria:

  1. PR Verification: Automatically triggers on pull requests to execute flake8 linting and 4 pytest unit tests (testing vocabulary, serialized model integrity, edge inference, and FastAPI health).
  2. Push to main: Automatically trains the model, serializes all formats, and uploads artifacts/ to GitHub Action Artifact storage.
  3. Tag-Based Staging Deployment: Triggering on version tags (e.g. v1.0.0), builds the Docker container and runs a live smoke test against /health.

7. Tool-Based Task: Production Apache Airflow DAG Orchestration

Implemented in dags/sentiment_mlops_dag.py inside an isolated container running apache/airflow:2.9.2:

  • download_data: Ingests raw sentiment dataset into data/raw_data.json.
  • preprocess_data: Tokenizes, generates vocabulary, and writes data/train_data.json.
  • train_model: Trains classifier, exports ONNX weights, and pushes test accuracy to Airflow XCom.
  • evaluate_model: Pulls accuracy from XCom and compares against baseline threshold ($0.85$).
  • check_accuracy_improvement (BranchPythonOperator): Quality gate routing to trigger_deployment when accuracy improves, or skip_deployment if performance regresses.
  • pipeline_complete: EmptyOperator with TriggerRule.NONE_FAILED_MIN_ONE_SUCCESS for clean graph convergence.

8. Comprehensive Jury Viva Defense Q&A

Q1: Why is Pickle prohibited for production model serialization?
Answer: Pickle serializes executable Python bytecode rather than static numerical arrays. Calling pickle.load() executes arbitrary code defined in __reduce__, creating a severe Remote Code Execution (RCE) vulnerability. In contrast, ONNX is a declarative Protocol Buffer graph specification that cannot execute arbitrary code.
Q2: Why is ONNX Runtime significantly faster than PyTorch on CPU?
Answer: ONNX Runtime applies graph-level optimizations prior to execution: constant folding, redundant node elimination, and operator fusion (combining operations into single kernel calls). Furthermore, it utilizes hardware-specific AVX2/AVX-512 SIMD vectorization and has zero Python interpreter overhead during inference.
Q3: How does the BranchPythonOperator prevent model regression in Airflow?
Answer: The BranchPythonOperator pulls the newly evaluated model's accuracy via Airflow XCom and compares it against the production baseline. If the new model fails to beat the threshold, it dynamically branches to skip_deployment, preventing degraded models from replacing working production artifacts.
Q4: What is the purpose of tag-based deployment in CI/CD?
Answer: Tag-based deployment ensures that regular commits or experimental branches do not accidentally trigger production/staging rollouts. Only formal semantic version tags (e.g. v1.0.0) trigger the container build and deployment pipeline after undergoing unit tests.
